# Placement System

A student placement and skill management system (MCA project).

Students see jobs they are eligible for, ranked by how well their skills match, and apply for them. Admins manage companies, jobs and students, move applications through the hiring stages, select candidates, and read placement statistics on a dashboard.

## Tech stack

| Layer | Technology |
|---|---|
| Database | SQL Server (Express). Database first: tables with constraints, indexes, views, functions, stored procedures |
| Backend | ASP.NET Core Web API on .NET 10, controllers + services, EF Core 10 (scaffolded from the database) |
| Auth | JWT bearer tokens, roles `Student` and `Admin`, passwords hashed with ASP.NET Core `PasswordHasher` |
| API docs | OpenAPI + Scalar (development only) |
| Frontend | To be added in `frontend/` |

## Getting started

### Prerequisites

- .NET 10 SDK
- SQL Server Express and SQL Server Management Studio (SSMS)
- Git

### 1. Create the database

Run the scripts in `database/` in order (`00` to `07`). Details are in `database/README.md`. Files `06` and `07` load development data and **delete existing rows**, so use them only on a development database.

### 2. Point the API at your SQL Server

Edit `backend/src/PlacementApi/appsettings.Development.json` and set your server name:

```json
"ConnectionStrings": {
  "PlacementDb": "Server=<your-server>\\SQLEXPRESS;Database=PlacementDb;Trusted_Connection=True;TrustServerCertificate=True;"
}
```

This uses Windows authentication, so no password is stored.

### 3. Set the secrets

Secrets are kept outside the repository with `user-secrets`. Run these from the `backend` folder:

```
dotnet user-secrets init --project src/PlacementApi
dotnet user-secrets set "Jwt:Key" "<at least 32 random characters>" --project src/PlacementApi
dotnet user-secrets set "SeedAdmin:Email" "admin@college.edu" --project src/PlacementApi
dotnet user-secrets set "SeedAdmin:Password" "<your admin password>" --project src/PlacementApi
```

On the first start, if no admin account exists, the API creates one from the `SeedAdmin` values.

### 4. Run

```
cd backend
dotnet watch --project src/PlacementApi
```

The API listens on `http://localhost:5283`. In development, an interactive API reference is available at `/scalar/v1`, and the OpenAPI document at `/openapi/v1.json`.

## Roles and business rules

| Rule | Where it is enforced |
|---|---|
| A student can apply only if CGPA is at least the job minimum, the job is open, the deadline has not passed, the student is active, and they have not applied before | `usp_ApplyForJob` (plus UNIQUE constraint as a safety net) |
| Applications move Applied, then Shortlisted, then Interview, and can be Rejected at any of those stages. Selected and Rejected are final | `usp_UpdateApplicationStatus` |
| Only an application at the Interview stage can be selected. Selecting changes the status and creates the placement in one transaction | `usp_SelectApplication` |
| A student may hold more than one placement (a second "dream offer") | Design decision |
| Placement percentage counts students placed; hiring numbers count offers | `vw_PlacementStatsByBatch`, `vw_CompanyHiringSummary` |
| Students can change only their phone number and skills. CGPA, roll number, email, course and graduation year are admin-controlled | `/api/me` endpoints |
| Deleting a company, skill or student only deactivates it (`IsActive = 0`) | Services |

## API overview

All endpoints except register, login and health need a valid token (`Authorization: Bearer <token>`).

| Area | Endpoints | Access |
|---|---|---|
| Auth | `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` | register and login public |
| Health | `GET /api/health` | public |
| Companies | `GET /api/companies`, `GET /api/companies/{id}`, `POST /api/companies` | read: any user, create: Admin |
| Skills | `GET /api/skills`, `POST`, `PUT /{id}`, `DELETE /{id}` | read: any user, write: Admin |
| Jobs | `GET /api/jobs/{id}` (any user); `GET /api/jobs`, `POST`, `PUT /{id}`, `PATCH /{id}/close` | Admin except single read |
| Students | `GET /api/students`, `GET /{id}`, `POST`, `PUT /{id}`, `DELETE /{id}` | Admin |
| Applications | `GET /api/applications`, `PATCH /{id}/status`, `POST /{id}/select` | Admin |
| Dashboard | `GET /api/dashboard/batch-stats`, `/company-hiring`, `/application-funnel` | Admin |
| Student area | `GET`/`PUT /api/me/profile`, `PUT /api/me/skills`, `GET /api/me/jobs/recommended`, `GET /api/me/jobs/{jobId}/skill-gap`, `GET`/`POST /api/me/applications` | Student |

List endpoints support `page` and `pageSize` (maximum 100).

## Error format

Errors are returned as `application/problem+json` with `status`, `title`, `detail` and, for database errors, an `errorCode`.

| Status | Meaning | Examples |
|---|---|---|
| 400 | The request is not allowed or invalid | CGPA below minimum, deadline passed, invalid status, validation errors |
| 401 | Missing, expired or invalid token, or wrong credentials | |
| 403 | Logged in but the role is not allowed | student calling an admin endpoint |
| 404 | Not found | unknown job, application or student |
| 409 | Conflict with the current state | duplicate application, already selected, stage change not allowed |
| 429 | Too many login or register attempts | 10 per minute per IP |

The numbered business errors (50001 to 50024) are listed at the top of `database/05_procedures.sql`.

## Database notes

- 9 tables with primary, foreign, unique and check constraints; junction tables for student skills and job skills.
- `Placement` references only `ApplicationId`; student, job and company are reached through joins, so they can never disagree.
- 5 nonclustered indexes for foreign keys and frequent filters. On 100,000 applications, listing applications for a job dropped from 567 to 3 logical reads.
- 5 views for reports, 2 inline table-valued functions for skill matching, 3 stored procedures for the business rules.
